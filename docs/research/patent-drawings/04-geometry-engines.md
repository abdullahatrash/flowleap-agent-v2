# 04 — Geometry engines for patent line art

Date: 2026-10-12. Scope: pick the engine that turns a model-written scene description into patent line art (black outlines on white, hidden lines removed, isometric and orthographic views, sections with hatching, exploded views, reference numerals with lead lines). Output chain: SVG, then PNG at 300 dpi, then PDF.

Constraints from the host app: the agent extension host is Node.js inside Electron. No Python runtime ships with the app. Native addons must be built for macOS, Windows and Linux on x64 and arm64, so they are a packaging risk. WebAssembly (WASM) and pure JS are fine.

Package metadata (version, date, license, unpacked size, dependencies) was read from the npm registry JSON on 2026-10-12 (`https://registry.npmjs.org/<name>`). Tarball file sizes were read with `tar tzvf` on the published tarballs. No package was installed or run.

## 2. Hidden-line removal in JS

- Exact vector HLR exists in exactly one place in the JS ecosystem: OCCT's `HLRBRep_Algo`, reachable through opencascade.js and wrapped by replicad `drawProjection`. OCCT notes that superimposed lines are not eliminated by this algorithm, so duplicate-segment cleanup in SVG is our job. [OCCT HLRBRep_Algo](https://dev.opencascade.org/doc/occt-7.9.0/refman/html/class_h_l_r_b_rep___algo.html)
- `@lnjs/core` 0.5.0 (ISC, 2020-06-22, no releases since) is a JS port of Fogleman's `ln`. `ln` hides lines by testing each sample point with a ray toward the camera against shape intersection functions; it outputs 2D paths. It handles Cube, Sphere, Cylinder and triangle meshes but is mesh-level, sample-based and unmaintained. [registry], [fogleman/ln](https://github.com/fogleman/ln)
- Web searches for a vector HLR SVG library in JS returned only forum threads (three.js pen-plotter clipping, Babylon edge tricks) and algorithm papers (Rankin 1987). No maintained library exists. [three.js discourse](https://discourse.threejs.org/t/hidden-line-segment-removal-for-meshes-pen-plotter-rendering/2000), [Babylon forum](https://forum.babylonjs.com/t/ideas-for-hidden-line-removal/9845)
- paper.js is 2D boolean geometry only; vsketch is Python; `hlr` on npm 0.1.1 is a React UI package, unrelated; `ln` on npm is a logging library. [registry]
- Mesh-based option if we chose manifold: write our own HLR (project triangles, clip each silhouette and crease edge against occluding triangles, emit visible fragments). This is a known 2.5D algorithm but it is new code with its own bugs, and curved surfaces produce faceted outlines.

## 3. The Python route (comparison only)

- CadQuery `exporters.export(shape, "x.svg", opt={"showHidden": True, "hiddenColor": ..., "projectionDir": (0.5,0.5,0.5), "strokeWidth": ..., "focus": ...})` gives visible and hidden lines from HLRBRep; `.section()` plus DXF export gives section curves. [CadQuery import/export](https://cadquery.readthedocs.io/en/latest/importexport.html)
- build123d `part.project_to_viewport(viewport_origin, viewport_up, look_at)` returns `(visible, hidden)` edge lists; `ExportSVG.add_layer(..., line_type=LineType.ISO_DOT)` styles hidden lines; `section()` gives the cross-section. No hatching. [build123d import/export](https://build123d.readthedocs.io/en/latest/import_export.html)
- OpenSCAD `projection(cut=true)` yields the z=0 slice as a 2D shape; `cut=false` a shadow. It is a 2D shape, not visible/hidden edges. [OpenSCAD manual](https://en.wikibooks.org/wiki/OpenSCAD_User_Manual/3D_to_2D_Projection)
- Why out: all three need a Python or native binary runtime. The `cadquery-ocp` wheel alone is 59–96 MB per platform and Python version, and a yanked release shows the wheel chain is fragile. The app ships no Python, so this route needs a sidecar installer per platform. OpenSCAD has an experimental WASM build (ochafik/openscad-wasm, Deno examples, Docker build) but it is a CLI image, not a library, and it still has no HLR. [cadquery-ocp on PyPI](https://pypi.org/project/cadquery-ocp/7.7.2.1), [openscad-wasm](https://github.com/ochafik/openscad-wasm)
- The useful lesson: both Python tools are thin wrappers around the same `HLRBRep_Algo` that replicad already exposes in JS.

Determinism: elkjs, dagre and Graphviz `dot` are deterministic for the same input and options (no randomised layouts in the layered algorithms; Graphviz `neato`/`fdp` are not needed). ## 7. Hatching for sections

Patent sections need the cut face as a closed polygon so we can clip 45° lines to it.

- manifold-3d: `slice(height)` returns a `CrossSection`; `toPolygons()` gives simple polygons with holes as separate contours. Rotate the solid so the cut plane is Z = h. The visible body behind the cut comes from `trimByPlane` on the same solid, then project that half. [manifold d.ts]
- replicad/OCCT: `cutShapeWithPlane` returns the kept half solid; the new planar face is in that solid's faces; `drawFaceOutline(face)` gives a closed `Drawing` with `toSVGPaths()`; `drawProjection` of the same half solid gives the visible edges behind the cut. Fillets and curved faces come out as exact curves. [operations.ts], [draw.ts]
- @jscad/modeling: no section operator. Workaround: `intersect(solid, thinSlab)` then `project()` yields the section as `geom2`; `project()` unions coplanar polygons so holes survive. [project.js]
- Python tools expose the same face (`section()`), and none of them hatches, so hatching is our SVG code in every stack: generate parallel lines over the polygon's bounding box and clip with an SVG `<clipPath>` holding the section polygon, or clip in code with a 2D polygon clipper (manifold `CrossSection` booleans or replicad `intersect2D`). Adjacent parts get opposite hatch angles or different spacing by part id.

## 9. Recommendation: two viable stacks

**Stack A (recommended): replicad on replicad-opencascadejs → own SVG writer → @resvg/resvg-wasm → pdfkit.**
- Everything we need is already a library call: solids with fillets and sweeps, `fuse/cut/intersect`, `drawProjection` with exact visible/hidden edges for front/top/side and isometric, plane cut plus `drawFaceOutline` for the section polygon, `Drawing.toSVGPaths` for paths. Numerals, lead lines, hatching and exploded offsets are our SVG layer. replicad-cli proves the headless Node path end to end.
- Main risk: size and licence. One 23 MB WASM (LGPL-2.1, dynamically loaded, must stay replaceable and credited) plus 5.9 MB JS in the extension host, with a first-load cost of seconds. Second risk: OCCT HLR can be slow on large assemblies and leaves superimposed duplicate segments; mitigate by projecting per part and de-duplicating segments in SVG. Third: replicad is a one-maintainer project (its `setXAxis` calls `SetYDirection`, a visible bug), so pin the version and keep our calls to the documented surface.

**Stack B (lean fallback): manifold-3d → own projection + own mesh HLR → same SVG/resvg/pdfkit tail.**
- 0.6 MB Apache-2.0 WASM, robust booleans, `slice()` gives the section polygon directly, `extrude`/`revolve`/`hull` cover most mechanical parts.
- Main risk: we must write and maintain hidden-line removal ourselves on triangle meshes (project, split edges against occluding triangles, keep silhouette and crease edges, drop tessellation edges). Curved parts render as facet outlines unless we post-filter by dihedral angle. No fillets or sweeps; those become extra mesh code. This is weeks of geometry work with its own defects; stack A gets it from OCCT today.

Not viable as the kernel: @jscad/modeling (no HLR, silhouette only), three-bvh-csg (experimental, DOM renderer), @lnjs/core (dead), mermaid (Chromium), any native rasteriser or Python sidecar.

Shared tail for both stacks: elkjs for block/flow diagrams with our SVG writer; @resvg/resvg-wasm with one bundled sans TTF passed via `fontBuffers` and `dpi: 300`; pdfkit for vector PDF with the same TTF embedded, A4 or Letter page sizes; pdf-lib only if a raster-in-PDF path is ever needed.
