# 05 — Sketch-to-geometry feasibility with today's vision LLMs

Date: 2026-10-12. Scope: can a BYOK frontier VLM (Claude, Gemini, GPT-class) read an inventor's hand sketch or photo plus a numbered parts list and write a structured geometry scene (box, cylinder, extruded polygon, revolve, tube; placement; numeral anchors) that a renderer turns into patent line art? Compared with the competitors' pixel route (sketch to line art by image-to-image diffusion). Sources are primary where possible; blog and vendor claims are marked `[blog]` or `[vendor]`.

## Verdict

- **The geometry route is feasible for simple parts and small assemblies, if the model writes code or a small DSL and a render-and-look loop closes behind it.** Frontier models execute valid CadQuery for 80–89 % of basic-geometry prompts and reach IoU 0.5–0.6 on them. They fall to about 30 % on complex topology ([Text2CAD-Bench, arXiv 2605.18430](https://arxiv.org/abs/2605.18430)).
- **Reading the sketch is the weak link, not writing the geometry.** Frontier VLMs score near chance on relative depth, multi-view and counting ([BLINK, ECCV 2024](https://arxiv.org/abs/2404.12390)), and fail when shapes touch or overlap ([Vision language models are blind, ACCV 2024](https://arxiv.org/abs/2407.06581)). The parts list and handwritten labels carry most of the meaning the model actually uses ([Picard et al., arXiv 2311.12668](https://arxiv.org/html/2311.12668)).
- **Executable is not correct.** Agents built a right-angle gearbox in 96.9 % of attempts and scored 4.0 % on the functional checks ([CAD-bench, ICML 2026](https://icml.cc/virtual/2026/77860)). A v1 needs structural checks (part count, anchor coverage, occlusion order), not only "it rendered".
- **The pixel route wins on first impression and loses on everything a patent figure must do:** a consistent second view, numeral anchoring, hidden lines, editability (section 3).

## 1. Published sketch-to-CAD and text-to-CAD work

| Work | Input → output representation | Reported accuracy | Failure modes |
|---|---|---|---|
| [Sketch2CAD](https://arxiv.org/abs/2009.04927) (SIGGRAPH Asia 2020) | Strokes drawn in context of the partial model → parametric CAD ops (extrude, cut, bevel, sweep) | Interactive, no LLM; trained only on synthetic line renderings | One operation per stroke set; not a one-shot reader |
| [Vitruvion](https://arxiv.org/abs/2109.14124) (ICLR 2022) | Raster hand-drawn sketch → 2D primitives + constraints | Accuracy on real hand drawings 47.0 % with clean renders, 65.5 % with a hand-drawn simulator, 75.9 % with affine augmentation (Table 2) | Non-axis-aligned lines; no 3D |
| [OpenECAD](https://arxiv.org/abs/2406.09913) (Computers & Graphics 2024) | Image → sketch-extrude command sequence, 0.55B–3.1B VLMs | Editable output, fed to CAD APIs | Sketch-extrude only |
| [Img2CAD](https://arxiv.org/abs/2408.01437) (2024, rev. 2025) | Photo → VLM predicts discrete program structure, transformer predicts continuous values → OpenCascade | ShapeNet common objects | Split into structure vs numbers because one model cannot do both |
| [Text2CAD](https://arxiv.org/abs/2409.17106) (NeurIPS 2024 spotlight) | Text → sequential sketch-extrude tokens; 170K DeepCAD models, 660K prompts | High validity, low geometric precision: 89–98 % executable but IoU 0.04–0.08 on Text2CAD-Bench | "Syntactically valid but geometrically imprecise" |
| [CAD-MLLM](https://arxiv.org/abs/2411.04954) (2024) | Text, multi-view image, point cloud → command sequence; Omni-CAD 450K | Beats conditional baselines on topology/enclosure metrics | Code release pending (third-party note) |
| [CAD-Recode](https://arxiv.org/abs/2412.14042) (ICCV 2025) | Point cloud → **CadQuery Python**, Qwen2-1.5B decoder, 1M procedural sequences | DeepCAD mean Chamfer 0.30 vs 3.43 prior, IoU 92.0 vs 77.6; real scans (CC3D) IoU 74.2 | No revolve or fillet in training data; B-splines invalid |
| [cadrille](https://arxiv.org/abs/2505.22914) (ICLR 2026 oral) | Point cloud / image / text → Python; SFT then online RL (GRPO) with programmatic reward | SOTA on 10 benchmarks incl. one real-world set | Needs an executable reward: the renderer is the grader |
| [CAD-Coder](https://arxiv.org/abs/2505.14646) (2025) | Image → CadQuery; 163K image–code pairs | Valid syntax 100 %, IoU-best 0.675 vs GPT-4.5 84 % / 0.524, Qwen2.5-VL-72B 94 % / 0.352 | Real photos score lower than renders; cannot add a fillet it never saw; training images are isometric gray renders only |
| [CADmium](https://arxiv.org/abs/2507.09792) (TMLR 2026) | Text → minimal **JSON** sketch-extrude history; Qwen2.5-Coder 1.5B–14B | Invalid rate 11.86 % → 3.33 % with scale; out-of-distribution (Fusion360) 12.58 % invalid | Sketch + extrude only; wrong hole counts and extra components (Appendix D) |
| [CAD-Llama](https://arxiv.org/abs/2505.04481) (2025) | Text → code-like loops of line/arc/circle + extrude | — | Same sketch-extrude ceiling |
| [LLM4CAD](https://par.nsf.gov/biblio/10661832) (ASME IDETC 2024, JCISE 2025) | GPT-4 / GPT-4V, text / sketch / image → CadQuery; shafts, nuts, flanges, springs, gears | Parse rate 0.543 (GPT-4V) vs 0.498 (GPT-4); 0.707 / 0.706 with a debugger loop. **Text-only beat text+sketch and text+image on average**; images helped only for springs and gears | Sketches were OpenCV sketch-style renders, not human; gears needed the `cq_gears` library |
| [CADCodeVerify / CADPrompt](https://arxiv.org/abs/2410.05340) (ICLR 2025) | Text → Python; 200 expert-written prompts; VLM writes yes/no questions about its own render, answers, fixes | GPT-4: −7.30 % point-cloud distance, +5.0 % success over prior work | Gains are real but single-digit |
| [CAD-Assistant](https://arxiv.org/abs/2412.13810) (ICCV 2025) | GPT-4o planner + FreeCAD Python tools; hand-drawn sketch parameterization task | Accuracy 0.784, Chamfer 0.680 vs Vitruvion 0.659 / 1.586 | Planner misreads its own renders (trapezoid read as triangle); GPT-4o mini gains little |
| [From Idea to CAD](https://arxiv.org/abs/2503.04417) (Honda Research, 2025) | **Hand sketches** (block, block with two holes, toy car) and **photos** (cap, bracket) + text → CadQuery via gpt-4o; QA agent renders 7 views | Qualitative only | "Struggle especially with the orientation of surfaces" (workplane choice); complex parts fail; faulty examples accumulate in context; hallucinated a `.bend` op |
| [Zoo Text-to-CAD / Zookeeper](https://zoo.dev/research/introducing-text-to-cad) `[vendor]` | Text → KCL code → B-rep; agent "frequently executes the model to check for errors" and reviews multi-view snapshots; mass/volume tools | No published accuracy | Image prompts "slated for the next update"; single parts, not assemblies ([Leo AI review](https://www.getleo.ai/blog/zoo-text-to-cad-review) `[blog, competitor]`) |
| Autodesk Project Bernini → "neural CAD" in Fusion ([Axios 2024](https://www.axios.com/2024/05/08/autodesk-ai-3d-models-bernini), [DE247 2025](https://www.digitalengineering247.com/article/autodesk-doubles-down-on-ai)) `[press]` | Text / image → mesh (OBJ), later editable CAD demo | Not shipped; no numbers | — |
| [ArtiCAD](https://arxiv.org/abs/2604.10992) (2026) | Text / image → articulated assemblies; a **Connector** fixes attachment points before geometry | Qualitative | Built explicitly "to get around the limited spatial reasoning" of LLMs/VLMs |
| [ASSEMCAD](https://arxiv.org/abs/2607.05123) (2026) | Text → typed parts, geometry-backed **ports**, executable mates, then CAD | Gains over code-centric baselines on its own AssemBench (unreleased) | States single parts work, "production-ready assembly generation remains largely unsolved" |

Benchmarks that grade frontier models directly:

- [Text2CAD-Bench](https://arxiv.org/html/2605.18430v1) (600 prompts, CadQuery): GPT-5.2 executes 88.9 % / IoU 0.59 at L1, 80.0 % / 0.50 at L2, 32.0 % / 0.23 at L3; Claude 4.5 Sonnet 79.7 / 0.54, 56.3 / 0.48, 30.0 / 0.25. Sweep, loft and shell make execution "plummet". The authors chose CadQuery because "code-based representations better leverage LLMs' pretrained capabilities".
- [BenchCAD](https://arxiv.org/abs/2605.10865) (17,900 CadQuery programs, 106 industrial part families): models "recover coarse outer geometry but fail to produce faithful parametric CAD programs", drop fine structure, and replace sweeps and lofts with extrudes.
- [RealCADBench](https://arxiv.org/abs/2609.03773) (12,632 tasks incl. 2D drawings and real product photos → FreeCAD Python): executability 0.565–0.812, solid IoU 0.28–0.54 across six frontier models; failures are missing fine structure, loss of part identity, wrong assembly placement.
- [CAD-bench](https://icml.cc/virtual/2026/77860) (ICML 2026, execution checks incl. pose, threads, rigid-body simulation): best standalone model 59.9 % overall, functional tasks near zero; the 96.9 % vs 4.0 % gearbox gap.

**Is code/DSL the representation that works?** Yes, on the evidence. Every result above IoU 0.5 comes from Python (CadQuery, FreeCAD, KCL) or a minimal JSON history, and the three 2026 benchmarks all chose code. Token-sequence models (Text2CAD, CADFusion) execute often but land far from the target shape. Fine-tuned small models beat GPT-4.5-class zero-shot on in-distribution images (CAD-Coder), but a BYOK product cannot fine-tune, so the frontier numbers above are the ceiling for v1.

## 2. Can frontier VLMs read an engineering sketch?

| Evidence | What it says about sketch reading |
|---|---|
| [BLINK](https://arxiv.org/html/2404.12390v3) (ECCV 2024, 14 perception tasks) | GPT-4V 51.26 % vs humans 95.70 %. Per task: counting 60.83 / 93.75, relative depth 58.87 / 99.19, spatial relation 72.03 / 98.25, multi-view reasoning 58.65 / 92.48, jigsaw 62.67 / 99.00 |
| [Vision language models are blind](https://arxiv.org/abs/2407.06581) (ACCV 2024) | Seven trivial tasks (do two circles overlap, how many times do two lines cross): four frontier VLMs average 58.57 %; Claude 3.5 Sonnet best at 74.01 %. Near 100 % once shapes are separated. Adjacent and overlapping parts are exactly the hard case in a sketch |
| [VSI-Bench](https://arxiv.org/abs/2412.14171) (CVPR 2025) | Spatial reasoning is "the primary bottleneck"; chain-of-thought and self-consistency do not help; asking the model to build an explicit cognitive map helps distance |
| [Picard et al.](https://arxiv.org/html/2311.12668) (MIT, 2023 preprint; AI Review 2025) | GPT-4V matched sketches to descriptions 10/10 **with** handwritten labels and 5.33/10 **without** (chance 2.5). The labels, not the strokes, carry the meaning. Sketch similarity judgments were 94 % self-consistent, better than human raters |
| [AECV-Bench](https://arxiv.org/abs/2601.04819) (2026, real floor plans) | OCR/text QA up to 0.95, symbol-centric counting of doors and windows 0.40–0.55: models "lack robust drawing literacy" |
| [Enginuity](https://arxiv.org/abs/2606.03410) (2026, military-manual diagrams) | Frontier VLMs locate labelled components reliably but are weak at describing and reasoning about the diagram |
| [OCRBench v2](https://arxiv.org/abs/2501.00321) (NeurIPS 2025) | 20 of 22 models score below 50/100; handwritten content extraction is called out as under-tested |
| [Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision) `[vendor]` | "Counting: approximate"; "Spatial reasoning: coordinate and localization outputs are approximate"; mistakes on rotated or sub-200 px images |
| [OpenAI vision docs](https://developers.openai.com/api/docs/guides/images-vision) `[vendor]` | "Struggles with tasks requiring precise spatial localization"; approximate counts; "may struggle to understand graphs or text where ... solid, dashed, or dotted lines vary" — the exact line vocabulary of patent drawings |
| [CAD-Assistant](https://arxiv.org/html/2412.13810v3) | Even with numeric IDs overlaid on its own render, the planner confused a trapezoid with a triangle |

Consequences for the reader step: counting parts and placing them relative to each other is unreliable from pixels alone; the numbered parts list must be the authority for *what exists*, and the sketch only informs *where*. Occlusion and hidden structure cannot be read; they must be derived by the renderer from 3D placement. Handwritten numerals should be transcribed in a separate OCR pass and cross-checked against the parts list, not trusted inline.

## 3. The pixel route, for comparison

- **What it is.** ControlNet adds spatial conditioning to a diffusion model ([Zhang et al., ICCV 2023](https://arxiv.org/abs/2302.05543)); the lineart checkpoint takes "black lines on a white background" and produces an image that follows them ([model card](https://huggingface.co/lllyasviel/control_v11p_sd15_lineart)). Patent vendors wrap this kind of model: PatentFig AI, DeepIP, Solve Intelligence all advertise sketch or photo → "compliant" line drawings in seconds ([DeepIP](https://www.deepip.ai/products/patent-drawings-generation), [Solve](https://www.solveintelligence.com/capabilities/figure-generation) `[vendor]`). A July 2026 RunDiffusion guide calls these "most useful for early drafting and review rather than final filing" `[blog]`.
- **What it does well.** Looks right fast, keeps the inventor's proportions, needs no parts list.
- **No consistent second view.** Each view is a fresh sample; Zero-1-to-3 "generates each novel view independently" and the views drift apart, and even tiled multi-view models still show "visible geometric inconsistencies" ([Zero123++](https://ar5iv.labs.arxiv.org/html/2310.15110)). A patent needs FIG. 1 and FIG. 2 to be the same object.
- **No numeral anchoring.** Pixels carry no part identity. The rules are structural: numerals not mentioned in the description "shall not appear", lead lines "must not cross each other" and must run "to the feature indicated", characters at least 0.32 cm ([37 CFR 1.84(p),(q)](https://www.law.cornell.edu/cfr/text/37/1.84)). Only a scene with named parts can enforce these.
- **No hidden lines or sections.** Occlusion is a 3D fact. The pixel model has no depth order, so it cannot decide which edge is dashed, where a section plane cuts, or what an exploded view separates ([1.84(h)](https://www.law.cornell.edu/cfr/text/37/1.84)). Design practice bans broken lines for hidden surfaces outright ([37 CFR 1.152 via MPEP](https://blueironip.com/mpep/mpep-9020-appx-r-1-152/)).
- **No editability or reproducibility.** Output is raster and stochastic; "move numeral 12" or "add part 14" means a new sample, not an edit.

## 4. Patterns that make LLM geometry generation work

1. **Render and look, with a checklist.** CADCodeVerify (+5.0 % success), SceneCraft (constraint score 26.1 → 64.5 when the render-review inner loop is on, [ICML 2024](https://arxiv.org/html/2403.01248v1)), Seek-CAD (step-wise perspective renders reviewed by a VLM, [arXiv 2505.17702](https://arxiv.org/abs/2505.17702)), Honda's 7-view QA agent, Zoo's multi-view snapshots. The local Anatomy skill does the same for 2D figures and adds what the papers lack: a fixed fault list to look for, in order (a line running into something, a crossing drawn behind, a seam that stops short of its edge, a mark that touches nothing), 4× zoom crops of joints, and a diff against the previous round's shot (`scratchpad/anatomy-src/references/verify.md`). Two limits from the papers: more iterations can hurt because "faulty examples accumulate in the context window" (Honda), and the critic itself misreads renders (CAD-Assistant, See-it-say-it-sorted). So cap rounds, send only the latest render, and keep the checks mechanical where possible.
2. **Truth model and parts list before geometry.** The Anatomy walkthrough builds a pure model first, then a 53-solid parts table grouped by sub-assembly, then a painter's order so the carriage sits *inside* the springs (`walkthrough.md` §1–6). Sketch2CAD observed the same designer habit: box-like primitives first, then cuts and roundings. SceneCraft plans a scene graph of relations, then turns it into numeric constraints. Img2CAD splits discrete structure from continuous numbers. For us: parts list → primitive per part → placement → anchors, each step checkable.
3. **A small DSL over a renderer beats raw CAD code for a product.** Text2CAD-Bench shows code leverages pretraining, but the same paper shows sweep/loft/shell collapse execution; CADmium shows a minimal JSON history is enough when the vocabulary is small. The Scene Language runs Claude 3.5 Sonnet on a DSL with no training ([CVPR 2025](https://arxiv.org/abs/2410.16770)); a Blender MCP author argues fixed typed tools give better feedback than free-form `bpy` scripts ([blender-ai-mcp](https://mcpservers.org/de/servers/patrykiti/blender-ai-mcp) `[blog]`). The five primitives in the brief are the right size: every op is executable, so the "invalid code" failure class disappears, and failures become shape errors the loop can see.
4. **Anchors as ports.** ArtiCAD predicts attachment points *before* geometry to dodge spatial reasoning; ASSEMCAD types parts and ports and executes mates deterministically. A numeral anchor (part, face, point) is the same idea: the model names the part, the renderer computes the lead line and keeps lead lines from crossing.
5. **Constraint checks that are not "did it render".** CAD-bench's lesson is the 96.9 % vs 4.0 % gap. Cheap structural checks for a figure: part count in scene = parts list; every numeral in the list has one anchor; no two primitives interpenetrate unless declared; bounding boxes overlap where the parts list says they touch; silhouette IoU against the sketch after alignment (CADCodeVerify and LLM4CAD both align before scoring).
6. **Part libraries, not generated parts.** SceneCraft's learned function library added 24.4 constraint points on top of the loop. LLM4CAD could only make gears through a library. BenchCAD's 106 industrial families are the catalogue to crib from: gear, spring, bolt, bearing, flange as parametric library calls.
7. **Text carries the intent.** LLM4CAD found text-only beat text+sketch; Picard found labels double accuracy. Feed the parts list and any dimensions as text, the sketch as support, and ask for a parts-first plan before any geometry.

## 5. Flowcharts from method steps

- Structure from numbered steps is near-trivial when the steps are given: fine-tuned image-to-Mermaid models reach node F1 ≈ 0.80 even from pictures ([model card](https://featherless.ai/models/DangIT02/qwen3vl-flowchart-to-mermaid_v2) `[blog]`), and FlowLearn reports Claude strong on nodes but ≈ 30 % F1 on links from images ([arXiv 2407.05183](https://arxiv.org/abs/2407.05183)). Edges, not boxes, are where models err.
- The known failure is invention: LLM-generated graph models "can include inaccurate, hallucinated elements" and violate structural constraints; the remedy is to sample several candidates and merge them ([arXiv 2508.00255](https://arxiv.org/abs/2508.00255)). In sketch-to-diagram runs, GPT-5 dropped a whole cluster of blocks and drew the wrong number of arrowheads, and Gemini 2.5 Pro added text it was told to leave out ([See it. Say it. Sorted, arXiv 2508.15222](https://arxiv.org/html/2508.15222v1)). EdgeFlow adds a parse-validate-repair loop on Mermaid ([arXiv 2605.27332](https://arxiv.org/pdf/2605.27332)).
- For v1: build nodes 1:1 from the claim steps deterministically; let the model only propose decision branches and loops; reject any output whose node count differs from the step count or whose labels are not substrings of the steps.

## 6. Realistic v1 expectation

| Sketch class | Expectation | Evidence |
|---|---|---|
| Flowcharts from numbered method steps | Works; nodes by construction, model only for branches | Section 5 |
| Simple housings, brackets, plates with holes (box, cylinder, extruded polygon) | Works with a render loop; expect one or two correction rounds | L1–L2 execution 80–89 %, IoU 0.5–0.6 (Text2CAD-Bench); Honda's block and block-with-holes succeeded; CAD-Coder IoU 0.5–0.7 on renders |
| Revolved parts (shafts, knobs, caps) | Works when the parts list gives diameters; weak from sketch alone | LLM4CAD shafts fine; CAD-Recode excludes revolve from training; frontier handles revolve as code |
| Assemblies of ≤ 15 distinct parts with a parts list | Works for placement *topology* (what touches what) with anchors-as-ports; placement *geometry* needs the loop and checks | RealCADBench: "incorrect assembly placement"; ArtiCAD/ASSEMCAD built connectors to avoid exactly this; Anatomy rig has 53 solids but was authored by hand with a truth model |
| Tubes, hoses, wires (sweeps) | Partial; expect straight segments and bends, not free paths | Sweep/loft "plummet" in Text2CAD-Bench; BenchCAD models replace sweeps with extrudes |
| Hidden lines, sections, exploded views | Works *because* the renderer derives them from 3D; do not ask the model for them | Section 3; 37 CFR 1.84(h) |
| Organic or freeform shapes (handles, ergonomic shells, enclosures with blends) | Does not work in v1 | L3 freeform ≈ 30 % execution, IoU 0.2–0.25; CAD-Coder cannot add a fillet it never saw |
| Complex mechanisms (gear trains, linkages, threads) | Does not work beyond a library call per standard part | CAD-bench functional tasks near zero; LLM4CAD needed `cq_gears` |
| Photos of real products | Does not work as the sole input; usable only with a parts list and expect lower fidelity | CAD-Coder: real photos lower than renders; RealCADBench photo regime at the low end; Honda's bracket photo produced a hallucinated op |
| Sketches with many touching or overlapping parts and no labels | Does not work; counts and adjacency will be wrong | BLINK counting 60.8 %; "blind" paper: failures concentrate where shapes touch; Picard: 5.33/10 without labels |

Open questions for the eval harness (next note): a silhouette-IoU gate against the aligned sketch, a parts-coverage gate against the list, and per-class pass rates with repeats, since a single run is noisy.
